ARCHITECTURE - A Collaborative Task Tracking System
====================================================

Project   : ACollaborativeTask-TrackingSystem
Stack     : Java 17, Spring Boot 4.1.1, Spring MVC, Spring Security (JWT),
            Spring Data JPA (Hibernate), MySQL, Maven
Arch style: Layered (3-tier) RESTful backend.

------------------------------------------------------------------------

2. LAYERED ARCHITECTURE
------------------------------------------------------------------------

   Request
   -------->
 [ Controller Layer ]  REST endpoints, request/response mapping (DTOs)
        |
        v
 [   Service Layer  ]  Business logic, validation orchestration,
 |                    transactions (@Transactional), authorization checks
        v
 [ Repository Layer ]  Spring Data JPA interfaces (CrudRepository/
 |                    JpaRepository) -> DB access
        v
 [   Database (MySQL) ]  6 tables (see Data Model)

Cross-cutting:
  - Security Layer   : JwtAuthenticationFilter -> SecurityFilterChain
  - Exception Layer  : @RestControllerAdvice -> GlobalExceptionHandler
  - Config Layer     : SecurityConfig, JwtConfig

------------------------------------------------------------------------

com.cts

 │    CommentController       /api/tasks/{id}/comments

 ├─ service/     (business logic)
 │    AuthService / UserService / TeamService / TaskService
 │    CommentService / AttachmentService
 ├─ repository/  (Spring Data interfaces)
 │    UserRepository / TeamRepository / TeamMemberRepository
 │    TaskRepository / CommentRepository / AttachmentRepository

 ├─ dto/         (records: request DTOs + response DTOs for each resource)
 ├─ security/    (JwtUtil, JwtAuthenticationFilter, CustomUserDetailsService)
 ├─ exception/   (GlobalExceptionHandler, ApiError, custom exceptions)
 └─ config/      (SecurityConfig, JwtConfig)

4. DATA MODEL / DATABASE SCHEMA (core tables)
------------------------------------------------------------------------

TABLE users          (id, email UNIQUE, username, password_hash(BCrypt),
                      first_name, last_name, created_at, updated_at)

TABLE teams          (id, name, description, owner_id FK->users, created_at)

TABLE team_members   (id, team_id FK, user_id FK, role ENUM(OWNER,MEMBER),
                      UNIQUE(team_id,user_id))

TABLE tasks          (id, title, description, status ENUM(TO_DO/IN_PROGRESS/
                      DONE), priority ENUM(LOW/MEDIUM/HIGH), due_date,
                      assignee_id FK->users (nullable), created_by FK->users,
                      team_id FK->teams (nullable), created_at, updated_at)

TABLE comments       (id, content, author_id FK->users, task_id FK->tasks,
                      created_at)

TABLE attachments    (id, file_name, file_type, file_url, size,
                      uploaded_by FK->users, task_id FK->tasks, uploaded_at)

(FUTURE) TABLE notifications  - deferred, see FUTURE SCOPE section.

Relationships
  users 1---------N teams        (owner)
  teams N---------N users        (members, via team_members with role)
  users 1---------N tasks        (created_by)
  users 1---------N tasks        (assignee)
  teams 1---------N tasks        (optional scoping of tasks to a team)
  users 1---------N comments
  tasks 1---------N comments
  tasks 1---------N attachments
  users 1---------N attachments (uploaded_by)

5. REQUEST FLOW EXAMPLES
------------------------------------------------------------------------

5.1 Login
  Client --POST /api/auth/login {email,password}--> AuthController
    AuthService verifies BCrypt hash -> JwtUtil issues token
    <-- 200 {accessToken, tokenType:"Bearer", user...} --> Client

5.2 Authenticated request (e.g., create task)
  Client --POST /api/tasks + "Authorization: Bearer <jwt>"--> JwtAuthenticationFilter
    Filter validates token -> sets SecurityContext Authentication
    TaskController -> TaskService (checks user, sets assignee/team)
      TaskRepository.save()  -> MySQL
    <-- 201 {task JSON} --> Client

5.3 Error handling
  Any exception -> GlobalExceptionHandler -> 400/401/403/404/409/500
  Consistent body: { "timestamp":..., "status":..., "error":...,
                     "message":..., "path":... }

------------------------------------------------------------------------
6. SECURITY ARCHITECTURE
------------------------------------------------------------------------
  - Stateless JWT (jjwt), secret in application.properties, expiry time
  - BCrypt password hashing (never store plaintext)
  - SecurityConfig:
        .csrf(disable) .sessionManagement(STATELESS)
        .authorizeHttpRequests: permit /api/auth/**, require auth for the rest
        addFilterBefore(JwtAuthenticationFilter, UsernamePasswordAuthenticationFilter)
  - Role-based checks: only team owner/manager can assign/remove members,
    task owner/assignee can update/delete
  - Input validation before any service call (@Valid on DTOs)

8. DEPLOYMENT / RUNTIME CONFIGURATION
------------------------------------------------------------------------
  - Java 17, Maven build (./mvnw spring-boot:run)
  - MySQL connection: URL/user/password via application.properties
  - Hibernate ddl-auto=update (dev) / validate (prod)
  - File storage: local uploads/ dir (configurable path), or cloud bucket
  - Port default 8080
  - Production: run via java -jar target/ACollaborativeTask-TrackingSystem-0.0.1-SNAPSHOT.jar

10. DESIGN PRINCIPLES FOLLOWED
------------------------------------------------------------------------
  - RESTful best practices (nouns, standard verbs, correct status codes)
  - Layered separation: controllers thin, services hold logic
  - DTOs decouple API contract from entities
  - Single source of truth for errors via @RestControllerAdvice
  - Stateless auth -> horizontally scalable
  - Code organized for maintainability (com.cts.* packages)
